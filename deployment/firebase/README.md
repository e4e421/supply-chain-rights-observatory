# Case desk rollout

The live pilot adds `/cases/` to the established portal. The original public collection, archive and Workbench continue in this stage. Submit only previously public material there. New private research belongs in the authenticated desk after cutover. The two workflow files beside this document are deployment templates, not active workflows.

## Prepare and verify the private backend

1. Select the team's Google account and create its Firebase project. Choose the Firestore (default) database location and access owners before provisioning. Enable email/password sign-in for pre-provisioned team accounts. Register a web app, record the project ID and its public web API key, and limit the key to the intended APIs and website. Do not put passwords, service-account keys or LLM keys in this repository.
2. Test the rules with a demo project first. From the repository root, run `firebase emulators:exec --project demo-scro --only auth,firestore 'python3 scripts/test_case_rules.py'`. Deploy just the reviewed rules to the intended new project with `firebase deploy --only firestore:rules --project PROJECT_ID`. Provision staff through the Firebase console. Create `members/{Firebase Auth UID}` with a string `role` equal to `researcher` or `editor`. Signup alone grants no data access. The server jobs use IAM, which bypasses client Security Rules.
3. Configure GitHub OIDC workload identity federation for this repository and its trusted main branch. Give the collector service account the minimum database read/write access for ingestion. Give the publisher read-only database access. Separate those service accounts and restrict who can impersonate each. Store repository variables `FIREBASE_PROJECT_ID`, `FIREBASE_WEB_API_KEY`, `GCP_WIF_PROVIDER`, `CASE_COLLECTOR_ACCOUNT` and `CASE_PUBLISHER_ACCOUNT`. `CASE_WATCH_HOSTS` is a comma-separated exact hostname allowlist for institutionally approved source monitoring. Unlisted hosts remain available for manual review.
4. Run `python3 scripts/private_collection.py inventory`. For the initial import on a trusted workstation use `FIREBASE_PROJECT_ID` and a short-lived `FIRESTORE_OAUTH_TOKEN` from the authorised Google account. Run `python3 scripts/private_collection.py migrate`. Check the counts and fingerprint reported by inventory against the `caseOps/migration` marker. Each batch compares the documents read back from the destination. Re-running the import preserves matching documents and stops on mismatches. Copy the current committed baseline once more at cutover to include any intervening public collection. The 12 historical decisions and catalogue metadata are separate documents.
5. Preview both `python3 scripts/build_case_release.py --firebase` and the rules test. Sign in as a researcher to create and edit a private draft, then as an editor to compare the proposed public packet, approve, correct and withdraw it. Verify an anonymous user and a signed-in nonmember cannot read the private queue. Validate that a unique private test marker appears in neither the public JSON nor HTML. The static publisher accepts only validated fields and refuses an invalid release. The browser keeps the ID token in memory and asks for a new sign-in after expiry.
6. After the import and permission checks, set `CASE_BACKEND=firestore`. Deploy the matching `refresh-and-publish.yml` and `monitor-freshness.yml` from this directory under `.github/workflows/` in the same reviewed change. Retire `publish-review.yml` and `propose-review.yml` and their public Issue-based submission route. Disable the public recovery export on push. Reconcile the frozen historical catalogue once more before starting collection. The replacement workflows write incoming sources to Firestore and upload only `_release/`. Successful deployment and the public manifest digest are independently checked. Never use `pilot` as a rollback for a previously connected backend with withdrawals; restore the prior verified publication instead.
7. Archive a verified private backup and test a restore before removing historical data from the current public repository. Existing Git history, forks, downloads, old public Issues and build artifacts are separate from the new publication. Review them explicitly with the owner; database migration cannot recall old copies.

## Tracking an event

In the private desk select or create a case, append an attributed milestone and its source, assign a follow-up date, and save. Use the full public packet editor for the location, rights holders, editorial question, corrections, and evidence URLs. Private notes and owner fields live outside that packet. A revision-checked save rejects stale edits. An editor's approval or withdrawal and its immutable audit entry are committed together. The next successful deployment reflects the decision. Publication, feed, observation and event dates have separate meanings. An undated action stays undated.

The private collector supplements the existing feeds with five English and local-language case queries. Their matches enter a private review queue. Approved source-page watches fingerprint content from permitted hosts respecting robots.txt. A content change creates a review task. Dynamic page changes can produce false alerts. A baseline, an inaccessible source and an unchanged source are recorded separately. The public queues show recent dated developments, due or overdue follow-up and missing worker, procedural, response or remedy evidence.

## Optional LLM evaluation

Use deterministic rules for IDs, dates, checksums, deadlines and duplicate observations. Use an LLM as a second reader for multilingual cross-document matching and bilingual milestone drafts after a researcher selects the public sources. Reviewers decide identity, unsupported allegations, conflicting evidence and remedy outcomes. By default the assistant runs a local shortlist, with no model request.

A local input file such as `.private/excerpts.json` uses this shape:

```json
{"sources":[{"id":"s1","visibility":"public","url":"https://example.org/case","excerpt":"A short, lawfully reusable, publicly available excerpt selected by the researcher."}]}
```

Run `python3 scripts/case_assist.py .private/excerpts.json` for the offline shortlist. On a trusted server only, configure `OPENAI_API_KEY` and a structured-output-capable `OPENAI_MODEL`; add `--invoke` to send a maximum of five selected excerpts and a bounded public case context. Add `--queue` to save the suggestion privately for editorial review. A refusal, incomplete response, absent supporting quote, out-of-packet reference or unsupported date cannot produce a publishable milestone. Exact quotes validate attribution, not the truth of a paraphrase. The model has no tools and no authority to approve a case. The request sets `store: false`; review the API provider's retention terms before live use. Execution is manual and usage counts are retained for evaluation. No model call runs on a schedule.

Run `python3 scripts/evaluate_case_matching.py` for the twelve authored regression examples. On a separate human-labelled sample, compare the local shortlist and API drafts on match precision/recall, unsupported facts or dates, duplicate alerts, editor time and actual cost per accepted update. Include lookalike factories, syndication, conflicting sources and unknown dates. Activate routine API calls only if verified time savings justify their cost and human review catches high-impact errors.
